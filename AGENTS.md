# Правила проекта Legamind

Эти правила обязательны для всех изменений проекта.

## 1. В проекте не должно быть известных багов

- Каждый баг сначала воспроизводится, затем исправляется **корневая причина**, а не симптом.
- Нельзя оставлять «потом исправлю», если сценарий уже сломан.
- Любое изменение проверяется:
  - `cargo test`;
  - `npx tsc --noEmit`;
  - E2E `e2e/run.ps1`;
  - ручной проверкой затронутого экрана/кнопки.
- Если баг нельзя исправить сразу — он фиксируется в отчёте как известное ограничение, а не выдаётся за рабочее.
- Не выпускать релиз с известным регрессом.

## 2. Вести проект так, будто я сам им пользуюсь

- Проверять реальные пользовательские сценарии, а не только компиляцию.
- Проверять первый запуск, установку, обновление, пустые состояния и ошибки.
- Не ломать существующие данные, сессии, настройки и модели.
- Любая функция должна быть понятна без чтения исходников.
- Если функция неудобна или скрыта — это баг UX.

## 3. Вести проект так, будто он должен быть самым лучшим

- Не добавлять функции «для галочки».
- Сначала надёжность, приватность и понятность, потом количество возможностей.
- Не копировать чужие приложения целиком; брать лучшие идеи и доводить до рабочего состояния.
- Каждый экран и каждая кнопка должны работать предсказуемо.
- Документация и отчёты должны соответствовать реальному поведению.
- Не заявлять о готовности без проверки.

## Обязательный цикл изменения

1. Понять сценарий и найти причину.
2. Внести минимальное изменение.
3. Добавить/обновить тест.
4. Прогнать тесты и вручную проверить UI.
5. Обновить документацию/отчёт.
6. Только после этого считать работу выполненной.

## Запрещено

- выдавать непроверенное за работающее;
- оставлять сломанные кнопки и мёртвые ссылки;
- скрывать ограничения;
- удалять данные пользователя без подтверждения;
- выпускать релиз без теста установки/обновления.

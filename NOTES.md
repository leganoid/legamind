# Отклонения от задания и проблемы машины

Документ фиксирует всё, что на этой машине отличается от TASK.md. Архитектура не менялась.

## 1. `aka.ms` недоступен по HTTPS

`winget install Microsoft.VisualStudio.2022.BuildTools` не работает: установщик качает манифест
канала с `https://aka.ms/vs/17/release/channel`, а соединение рвётся (HTTP-вариант при этом
отдаёт 302 на CDN, и `download.visualstudio.microsoft.com` доступен).

Обход, применённый здесь (без изменения задания):

1. `vs_BuildTools.exe` скачан по `http://aka.ms/vs/17/release/vs_BuildTools.exe`.
2. Манифест канала скачан по `http://aka.ms/vs/17/release/channel` и роздан локально:
   `python -m http.server 8123` в `.tools`.
3. Установка: `vs_BuildTools.exe --quiet --wait --add Microsoft.VisualStudio.Workload.VCTools
   --includeRecommended --channelUri http://127.0.0.1:8123/channel.json`.
4. Windows SDK (10.0.28000.0) взят NuGet-пакетами `Microsoft.Windows.SDK.CPP`,
   `Microsoft.Windows.SDK.CPP.x64`, `Microsoft.Windows.SDK.BuildTools` в `.tools/sdk`
   (VS-инстанс не зарегистрирован, `vswhere` его не видит).

## 2. Окружение сборки Rust

Из-за п.1 `rustc` не находит MSVC автоматически. Поэтому:

* `.cargo/config.toml` задаёт линкер, `INCLUDE`, `LIB`, `CC` абсолютными путями;
* `scripts/env.ps1` выставляет то же самое + `PATH` для `rc.exe` и `cl.exe`.

`cargo build` из «чистой» консоли без этих переменных работать не будет — это ограничение машины,
а не проекта.

## 3. Ошибка D8050 при компиляции C-кода

`cl.exe` из Build Tools 14.44 падал с
`error D8050: нельзя выполнить c1.dll: не удалось поместить командную строку в запись отладки`
при компиляции `sqlite3.c`/`ring` через `cc` с `/Z7` (отладочная информация C).
Решение: `[profile.dev] debug = 0` в `src-tauri/Cargo.toml` (для C-кода отладочная информация
выключена; на разработку это не влияет).

## 4. `reqwest` без rustls

В `TASK.md` указаны только фичи `json`, `stream`. Собрано именно так (TLS — системный,
через `native-tls`/SChannel): это и ближе к заданию, и не тянет `ring` с C-сборкой.

## 5. Node.js 26 вместо 22

`winget` в канале LTS отдал Node.js 26.13.0. Требование «20+» выполнено, Vite 7 и Tauri CLI 2.12
работают.

## 6. `tauri-cli` из npm

`cargo install tauri-cli` не выполнялся: тот же CLI (`tauri-cli 2.12.4`) приходит как
`@tauri-apps/cli` в devDependencies, и `npx tauri dev` / `npx tauri build` — его точные аналоги.

## 7. Запуск приложения из-под песочницы DSH

Обнаружено: процессы, запущенные **из папки проекта**, в этой сессии ограничены файловой
песочницей DSH (запись только в workspace). Из-за этого приложение падало на создании БД в
`%APPDATA%` и на WebView2 (ошибки `os error 5`, `0x800700AA`, `0x8000FFFF`).
Собранный exe, скопированный за пределы workspace (и установленный `.msi` из `Program Files`),
работает нормально. Это ограничение среды разработки, а не приложения; в README описан обход.

Проверено: `Legamind_0.1.0_x64_en-US.msi` устанавливается (`msiexec /i ... /qn`, код 0),
кладёт `legamind.exe` и папку `engine` в `C:\Program Files\Legamind`, установленное приложение
запускается, поднимает сайдкар из своих ресурсов и отвечает на `/health`.

## 8. Зависание загрузки тяжёлых моделей (исправлено)

В `engine/manager.py` `ensure_loaded` брал `_global_lock`, а затем `_evict_for` брал его повторно —
`threading.Lock` нереентерабельный, поэтому загрузка любой модели тяжелее 8 ГБ (14B, 30B) вставала
навсегда (лёгкие модели не задевали ветку выгрузки). Исправлено: `_evict_for_locked` вызывается
только под уже взятым локом. Проверено: `qwen3-14b` грузится за 5–8 с (кэш), отвечает 2–3 с.

## 9. Вывод сайдкара

Изначально stdout/stderr сайдкара читались пайпом. После строки `READY` читатель закрывался,
и любая последующая запись в stdout могла заблокировать процесс (переполненный пайп).
Сейчас stdout/stderr перенаправлены в файлы `logs/engine_stdout.log` и `logs/engine_stderr.log`,
а порт читается из файла — блокировка исключена.

## 10. Лимит промпта на NPU (исправлено)

По умолчанию NPU-пайплайн принимает промпт не длиннее 1024 токенов
(`Stateful LLM pipeline on NPU may only process prompts ... up to 1024 tokens`), из-за чего
дебаты с `local/qwen-1.5b` падали на раунде голосования. Теперь для устройств NPU
менеджер передаёт `MAX_PROMPT_LEN=4096` и `MIN_RESPONSE_LEN=256` — проверено на реальном
дебате (2 участника, 2 раунда, голосование, вердикт).

## 11. Кэш моделей провайдера (исправлено)

По TASK.md 5.4.4 успешная проверка соединения должна сохранять список моделей в `provider_models`,
чтобы они сразу появились в выборе. Изначально это делал только `provider_refresh` («Обновить модели»).
Теперь `provider_check` сохраняет список, если провайдер уже есть в БД, а `provider_save`
дополнительно подтягивает модели сразу после сохранения. Проверено в UI: «Проверить» → 2 модели,
«Сохранить» → `provider_models` заполнена, `mock-fast`/`mock-smart` видны в выборе модели.

Заодно `delete_key` теперь удаляет запись `secret_dpapi:*` из `settings`, а не оставляет пустую.

## 12. Разрыв UTF-8 на границе чанка (исправлено)

Парсер SSE декодировал каждый сетевой чанк отдельно через `String::from_utf8_lossy`.
Если кириллица попадала на границу чанка (обычное дело в TCP), символ превращался в `�`.
Нашлось тестом Anthropic-потока с нарезкой по 40 байт. Теперь байты копятся в `Vec<u8>`,
декодируется только корректно завершённая часть, хвост переносится в следующий чанк
(`decode_stream_chunk`). Тест `tests/anthropic_e2e.rs` — зелёный.

## 14. Скиллы и слэш-команды (добавлено после MVP)

**Скиллы.** Навык — это набор инструкций, который подмешивается в system-промпт. Конструктор
хранит части отдельно: `name`, `description` (когда применять), `role`, `guidelines`,
`output_format`, `examples`, `constraints`, `triggers`. В промпт собирается единый блок
`### <название>` с бюджетом 4000 символов. Если у навыка заданы триггеры (через запятую),
он подключается только когда сообщение пользователя содержит хотя бы одно слово; без триггеров
работает всегда. Таблица `skills` появилась миграцией схемы v2, три встроенных навыка
(«Кратко», «Код-ревью», «Тьютор») создаются выключенными.

Импорт: экран «Скиллы» → «Импорт SKILL.md» — frontmatter `name`/`description` и тело markdown
раскладываются по полям конструктора. Экспорта обратно в SKILL.md пока нет.

**Команды.** Слэш-команды обрабатываются в Rust (`chat_command`), в историю попадают только
результаты, требующие сохранения:

| Команда | Что делает |
|---|---|
| `/help` | список команд |
| `/compact` | модель пересказывает последние ≤40 реплик (≤12k символов), старая история удаляется, остаётся одно сообщение со сводкой; эпизод пишется в память |
| `/clear` | удаляет все сообщения сессии |
| `/remember <текст>` | сохраняет факт в память |
| `/skills`, `/skill <название>` | список навыков и включение/выключение |
| `/export` | выгружает переписку в `%APPDATA%\com.legamind.app\exports\chat-<id>.md` |

Проверено в живом приложении: `/help` показывает баннер со списком; `/compact` на реальной
модели Qwen3-14B сжал 2 сообщения в сводку (Цель / Решение / Факты / Незавершённые задачи /
Детали), индикатор контекста уменьшился; включение навыка «Кратко» добавило в `prompts.log`
блок «Активные навыки (следуй им): ### Кратко».

## 15. Обучение: правила и дообучение

«Обучение» в Legamind разделено на два принципиально разных механизма.

**1. Самообучение без градиентов (работает сразу).** Оценка 👎 у ответа с комментарием создаёт
правило (`lessons`): текст комментария сохраняется и подмешивается в system-промпт блоком
«Усвоенные правила (соблюдай):» (бюджет 1500 символов). Правила можно включать/выключать и
удалять, в чате 👍/👎 ставятся на каждый ответ. Это меняет поведение сразу, но не веса:
14B int4 в IR-формате дообучить нельзя (это inference-формат).

**2. Дообучение весов через дистилляцию.** Датасет генерирует модель-учитель (облачная платная
или локальная): пары «инструкция → ответ» по вставленному материалу или по выбранной сессии,
до 200 примеров, JSONL формата `{"messages": [...]}`. Файлы — в
`%APPDATA%\com.legamind.app\datasets\`. Прогресс приходит событием `dataset:progress`.

Дальше обучение — вне приложения, скриптами:

```
pip install torch transformers peft datasets optimum-intel nncf
python scripts/finetune_qlora.py --dataset <jsonl> --base <HF-веса> --output adapters/<name> --epochs 2
python scripts/export_openvino.py --base <HF-веса> --adapter adapters/<name> --output C:\Models\<name>-int4-ov
```

Почему не в приложении: нужны исходные HF-веса (IR-папки не подходят), PyTorch с XPU/CUDA и
часы обучения; это отдельная тяжёлая установка. Экран «Обучение» проверяет наличие пакетов
(`finetune_status`), показывает Python/устройство/HF-веса и готовые команды; пустой ответ
пробы больше не считается «готово» (баг найден при проверке: `find_spec("optimum.intel")`
бросает ImportError, если нет `optimum`, — обёрнуто в try/except, а отсутствие ответа теперь
означает «не готово»).

Импорт готовой IR-папки в реестр моделей пока вручную (правка `engine_config.json`);
автоматическое добавление — следующий шаг.

### Извлечение обучения из готовой сессии

Отдельный поток «Из сессии: итоговый результат» в отличие от генерации «с нуля» берёт **готовый
диалог** и вытаскивает из него только финальные решения (код, команды, конфиг, шаги), без
промежуточной отладки. Модель-учитель возвращает 1–3 пары `instruction` (самодостаточная
постановка задачи) + `answer` (итог целиком), с ограничением «если итог не ясен — пустой список».

Защита от мусора и дублей:

* **дубли между кандидатами и уже собранными датасетами** — сходство Жаккара по словам
  (слова длиной ≥4, нижний регистр); порог показа 0.55, порог отказа при добавлении 0.75;
* **проверка «модель это уже умеет»** — кнопка просит локальную модель ответить на инструкцию
  самостоятельно, затем считается покрытие слов эталона (`coverage`) и Жаккар: ≥0.6/0.5 —
  «уже умеет», ≥0.35 — «частично», иначе «новое». Это эвристика: правильный, но иначе
  сформулированный ответ может получить низкое покрытие, поэтому финальное решение — за человеком;
* предупреждения о коротком ответе/инструкции и остатках `<think>`-тегов;
* **ручное подтверждение**: «Принять в датасет» (в существующий или новый) или «Отклонить».
  Принятая пара сразу дописывается в JSONL и увеличивает счётчик примеров.

Это ровно тот сценарий «мы с ИИ дошли до решения, ресурсы подтягивались из интернета»: в обучение
попадает итог, а не весь путь, и только если он не дублирует уже собранное и не выглядит как
«модель и так умеет».

## 16. Интернет для локальных моделей

Перед ответом модели выполняется поиск по последнему сообщению (если оно не короче 10 символов
и не «привет»-подобное). Найденные сниппеты вставляются в system-промпт блоком
«Актуальные данные из интернета (запрос, дата)», а ссылки пишутся в `message_sources` и
показываются под ответом. Токены поиска съедают часть бюджета контекста — это видно по индикатору.

Провайдеры: Yahoo HTML (ключ не нужен, релевантная выдача), Wikipedia API, Stack Exchange API,
GitHub API, SearxNG (свой инстанс, JSON), Tavily/Brave (ключи в Credential Manager),
Bing/DDG как best-effort. «Авто» перебирает по порядку и возвращает первый непустой результат.

Почему так: с этой сети DDG отдаёт 202/challenge, Mojeek — captcha, Bing — нерелевантную
выдачу, публичные SearxNG — 429/HTML вместо JSON, Jina — 451. Yahoo и Wikipedia работают;
для стабильного «глобального» веба нужен свой SearxNG или ключ Tavily/Brave — тогда они идут
первыми в цепочке.

Безопасность: `web_fetch_page` разрешает только http/https и блокирует localhost/частные
диапазоны (SSRF-guard); в чат пока идут только сниппеты выдачи, полное чтение страниц —
отдельная команда (кандидат на tool-loop в M6). Приватность: текст запроса уходит провайдеру
поиска; отключается тумблером.

## 19. Рабочая папка сессии

У каждой сессии может быть свой каталог проекта (`sessions.workdir`, схема v5). Выбор — кнопка
**📁** в шапке чата: открывается нативный диалог (rfd), при отмене — ввод пути вручную; рядом
кнопка **↗** открывает папку в проводнике. Команды: `/pwd`, `/workdir <абсолютный путь>`.

При выборе папки создаются:

```
<проект>/
  .legamind/session.json   — связь папки с сессией (id, модель, дата)
  .legamind/README.md
  exports/                 — /export кладёт переписку сюда
  datasets/                — датасет, сгенерированный из этой сессии
  notes.md                 — заметки проекта (создаётся, если нет)
```

Папка создаётся, если её нет (кроме случая, когда путь относительный — это ошибка).
Канонический путь хранится без Windows-префикса `\\?\`. Модель пока не пишет в папку
сама: файловые инструменты — следующий шаг (M6), рабочая папка станет их корнем.

## 20. Google и Яндекс как поисковые провайдеры

HTML-выдача обоих поисковиков без ключей не работает: Google отдаёт JS-оболочку (`enablejs`),
Яндекс — капчу (35 маркеров `showcaptcha`). Поэтому:

* **Google** — через Custom Search JSON API: нужны API-ключ (`web:google` в Credential Manager)
  и CX (Programmable Search Engine ID, хранится в настройках). Запрос:
  `GET https://www.googleapis.com/customsearch/v1?key=…&cx=…&q=…`; разбор `items[].title/link/snippet`.
* **Яндекс** — best-effort HTML (`yandex.ru/search/?text=…`), парсер `li.serp-item` /
  `OrganicTitle-Link` / `OrganicText`. При капче возвращается понятная ошибка с советом
  использовать Google CSE/Tavily/Brave/SearxNG.

Оба добавлены в «Авто»: Google — сразу после Brave (только если заданы ключ и CX), Яндекс —
после GitHub, Yahoo остаётся последним резервом. В настройках у Google появились поля
«Google API-ключ» и «Google CX», у Яндекса — отдельный провайдер с пометкой о капче.

Проверено в UI: выбор Яндекса даёт «Яндекс показывает капчу…», выбор Google без ключа —
«Нужен ключ Google Custom Search (и CX)…»; ошибки видны в карточке проверки, а не теряются.

## 21. Панель сессии: режим, рассуждения, доверие, орфография

Под шапкой чата появилась строка управления сессией (`sessions.mode`, `sessions.trust`,
`sessions.reasoning`, схема v6):

* **Режим** — `chat` (общение), `plan` (планирование: план шагами, без финального кода),
  `build` (создание: сразу рабочий результат), `review` (ревью: ошибки и риски). Текст режима
  добавляется в system-промпт; проверено по `prompts.log` («Режим «Планирование»…»).
* **Рассуждения** — уровни берутся из `/models` провайдера (`effort.supported_levels`), поэтому
  DeepSeek показывает «Авто / Низкое / Среднее / Максимальное» и отправляет `reasoning_effort`.
  Локальные думающие модели — «Без размышлений / С размышлениями» (поле `think`). Для MiMo
  уровни появятся автоматически, если провайдер их рекламирует: без ключа `/models` отдаёт 401,
  поэтому список сейчас не проверить.
* **Доверие** — `read_only` / `workspace` / `full`. Политика уже применяется приложением:
  при `read_only` запрещены `/export` и `/workdir` (проверено: понятная ошибка в чате);
  `full` включается только после подтверждения и показывает красный бейдж. Файловые инструменты
  модели (M6) будут проверять эту же политику перед записью/удалением.
* **Орфография** — у textarea включён `spellcheck`, `lang="ru-RU"`, в WebView2 добавлены
  `--enable-spell-checking --lang=ru`; подчёркивания рисует словарь Edge/Windows (при наличии
  русского языкового пакета).

## 23. Дебаты: текст облачных моделей и судья

Причина пустых реплик DeepSeek: reasoning-модели стримят размышления в
`choices[0].delta.reasoning_content`, а `delta.content` при исчерпании лимита остаётся пустым.
`consume_openai_stream` теперь читает оба поля: reasoning оборачивается в `<think>…</think>`,
при появлении `content` блок закрывается. UI сворачивает его в «Рассуждения модели»
(`details`), поэтому текст виден, но не мешает.

Заодно: лимит на реплику поднят 768 → 1536 (clamp 256…4096, UI до 4096), дебаты рендерят
markdown, а селект судьи использует `selected` на опциях — выбор больше не сбрасывается
после подгрузки списка моделей (та же проблема была у «Рассуждений» в чате).

## 24. M6 (первый срез): инструменты файлов с подтверждением

`src-tauri/src/tools.rs`: `list_dir`, `read_file`, `write_file`. Модель вызывает их JSON-блоком
```tool {"tool":"read_file","path":"src/main.rs"}```; протокол описан в system-промпте, когда у
сессии задана рабочая папка. Поддерживаются `read_only / workspace / full`: вне рабочей папки
писать/читать нельзя (кроме `full`), абсолютные пути — только при `full`.

Запись всегда проходит через подтверждение: событие `tool:approval` с diff, модалка в UI,
ответ через `tool_approve` (oneshot, таймаут 180 с — иначе отказ). Действия пишутся в
`audit.log`. Чат-цикл делает до 4 раундов инструментов; результат инструмента добавляется
как пользовательское сообщение, финальный ответ стримится одним блоком.

Проверено: запрос «Create checklist.md with three steps» → DeepSeek вызвал `write_file`,
появилась модалка, после «Разрешить» создан `checklist.md` (686 Б, UTF-8), в `audit.log`
запись `write … (686 B)`. Тесты: парсер вызовов, песочница путей (`../`, абсолютные),
diff — 56 unit.

### M6, второй срез: apply_patch и run_command

* `apply_patch` — точечная правка: `old` должен встречаться ровно один раз (0 или >1 — внятная
  ошибка), diff показывается в том же окне подтверждения. Пути и лимиты те же.
* `run_command` — `cmd /C <command>` в рабочей папке, таймаут 60 с, stdout+stderr в ответ
  (до 8000 символов), подтверждение показывает команду и cwd. При `read_only` команды запрещены.
* Подтверждение обобщено: `ApprovalPayload.kind` = `write` | `command`, в модалке либо diff,
  либо команда и папка. Все действия (write/patch/command, а также отказы) — в `audit.log`.

Проверено вживую с DeepSeek: `apply_patch` дописал строку в `checklist.md` (699 Б, diff
подтверждён), `run_command` выполнил `echo hello-from-legamind` (exit 0, вывод пришёл в ответ).
Тесты: 58 unit (уникальность фрагмента, read_only, простой `cmd /C echo`).

### M6, третий срез: история инструментов

Таблица `tool_runs` (схема v8) хранит каждый вызов: инструмент, путь, ok, summary, output.
`execute_call` пишет запись независимо от успеха (ошибки — с ok=false), а чат при наличии
рабочей папки добавляет в system-промпт блок «Что уже делали с файлами в этой сессии»:
последние 5 вызовов с усечёнными выводами (до 400 символов каждый, общий бюджет ~3500).
`/clear` очищает и историю инструментов.

В UI появилась кнопка **🧰 История** в панели сессии: модалка с последними 20 вызовами
(✓/✗, инструмент, путь, время, summary). Команда `tool_runs_list`.

Проверено: `read_file checklist.md` записан в `tool_runs`; на следующем сообщении в
`prompts.log` строка `=== tools … history_runs=1`; модель в ответе перечислила
`read_file`, `write_file`, `apply_patch`, `run_command`. Модалка истории показывает

### M6, четвёртый срез: несколько правок, удаление и переименование

* `apply_patch` принимает `patches: [{old,new}, …]` — несколько фрагментов за один вызов,
  diff по итоговому файлу, одно подтверждение.
* `delete_file` — удаление файла; подтверждение показывает путь, размер и diff (все строки
  как удалённые).
* `rename_file` — `path` + `new_path`; подтверждение «Переместить: a → b», цель не должна
  существовать, родительские папки создаются.
* Модалка подтверждения понимает `kind = write | command | delete | move` и подписывает
  кнопку соответственно («Разрешить запись», «Выполнить», «Удалить», «Переместить»).
  Audit: `delete`, `move` и отказы.

Проверено вживую: `rename_file checklist.md → checklist-old.md` (подтверждено, файл переехал),
затем `delete_file checklist-old.md` (подтверждено, файл удалён, 699 B). В `audit.log` записи
`move … → …` и `delete … (699 B)`. Тесты: 60 unit (несколько фрагментов, delete/move, read_only).

### M6, пятый срез: резервные копии и «Отменить последнее»

Перед каждой записью/правкой/удалением/перемещением файл копируется в
`<workdir>/.legamind/backups/` (для новых файлов копии нет — откат удаляет созданный файл).
Метаданные — таблица `tool_backups` (схема v9): действие, путь, цель, backup_path, created, undone.

Команда `tool_undo_last` восстанавливает последнее неотменённое изменение:
write/patch → вернуть старую версию (или удалить созданный файл), delete → восстановить,
move → вернуть на прежнее место. Кнопка **↩ Отменить** в панели сессии (с подтверждением),
в audit.log — `undo <action> <path>`. Повторная отмена идёт к предыдущему изменению.

Проверено вживую: созданный `undo-test.txt` после «Отменить» исчез, audit `undo write …`;
unit-тест покрывает write/create/delete/move (61 тест).

### M6, шестой срез: политика команд и очистка бэкапов

`guard_command` проверяет команду до подтверждения. Заблокированы навсегда (даже при `full`):
`format`, `diskpart`, `bcdedit`, `vssadmin`, `wbadmin`, `cipher /w`, `reg delete`,
`reg add HKLM`, автозапуск через HKCU Run, `shutdown`, `restart-computer`, `sc delete`,
`schtasks /delete`, `taskkill /f`, `net user/localgroup`, `takeown`, `icacls`,
`rm -rf /`, `rm -rf ~`, `del/rd /s /q C:\`, `powershell -enc`, `curl | cmd`, `iwr | iex`.
Отказ пишется в audit как `command_blocked` и возвращается модели как ошибка инструмента.

Потенциально разрушительные (`del`, `rm`, `git reset --hard`, `git clean`, `git push --force`,
`npm/cargo publish`, `pip/npm install`) разрешены, но в модалке подтверждения показывается
красное предупреждение.

Бэкапы чистятся автоматически: `prune_backups` оставляет 20 самых свежих файлов в
`<workdir>/.legamind/backups`.

Проверено: unit-тесты (guard блокирует `format`, предупреждает `del`, prune оставляет 2 из 5);
в живом чате модель сама отказалась выполнять `format C: /q` (дополнительный слой защиты).

### M7: локальный RAG по проекту

Без внешних эмбеддингов: файлы рабочей папки режутся на чанки (~900 символов, перекрытие 150,
по границе строки) и кладутся в SQLite FTS5 (`rag_chunks` + виртуальная `rag_fts`, схема v10).
Индексируются текстовые расширения (md/txt/rs/ts/tsx/js/json/toml/py/css/html/yml/sql/…),
пропускаются `.git`, `node_modules`, `target`, `.legamind`, `dist`, `build`, `.venv`, файлы >256 КБ;
лимиты 400 файлов / 2000 чанков.

Перед ответом в tool-сессиях выполняется поиск по последнему сообщению (BM25, топ-5) и в
system-промпт добавляется блок «Релевантные фрагменты проекта» с путями (до ~4500 символов).
В `prompts.log` — `rag=true/false`. Кнопка **📚 Индекс** в панели сессии запускает
`rag_reindex` и показывает «N фрагментов из M файлов»; `rag_status` — текущие размеры индекса.

Проверено: demo-project проиндексирован (5 чанков / 4 файла), на вопрос «Что написано в

### Шифрование резервных копий (DPAPI)

* Все копии (ручные, автокопии, страховочная перед восстановлением) пишутся в формате
  `LMENC1\n` + DPAPI-блоб (`CryptProtectData`, привязка к пользователю Windows).
* Открытый SQLite-файл создаётся только как временный и сразу удаляется; в папке копий
  plaintext не остаётся.
* Восстановление автоопределяет формат: зашифрованный файл расшифровывается во временный и
  подаётся в SQLite backup API, старые незашифрованные копии по-прежнему принимаются.
* UI и Help явно сообщают, что копии зашифрованы и открываются только под вашей учётной записью.

Проверено: `auto-20261031-130141.db` начинается с `LMENC1`, SQLite его не открывает
(«file is not a database»), размер 418 КБ; unit-тест шифрованная копия → восстановление
проходит. Тесты: 73 unit.

### Разумный баланс шифрования копий

* Ручная копия по умолчанию — **обычный SQLite-файл**: открывается сторонними инструментами,
  переносится на другой ПК, восстанавливается где угодно. Шифрование DPAPI включается галочкой
  «Шифровать ручную копию».
* Автокопии (служебные, в папке данных) остаются зашифрованными DPAPI.
* Восстановление принимает оба формата; перед восстановлением страховочная копия тоже
  шифруется (служебная).
* UI и Help поясняют разницу: ручная — для переноса, автокопии — для страховки на этой машине.
